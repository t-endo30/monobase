# 記事作成プロンプト（モノベース標準）

**このファイルが、モノベースの記事すべての標準フォーマットです。**
`tools/write_article.py`（手元・週次の自動生成）と管理画面の「プロンプトで本文を作る」
「URLから記事を作る」は、いずれもこのファイル全文を生成AIに送っています。
以降に作る記事は、新旧を問わずこの形式に揃えます。

生成AIに書かせるときは、このプロンプトの `[ ]` を埋めて使う（`write_article.py` が自動で埋めます）。
出力された内容を `admin.html` の各フィールドに貼り付けるか、`content/articles.json` に直接転記する。

---

## このサイトの記事の性格

**結論ファースト**で、**流し読みでも要点が拾える**記事にします。
読者は「まず結論を知りたい」「自分は買いなのかを最短で判断したい」と考えています。
冒頭を読んだだけで「評価」「3行の結論」「良い点・気になる点」「どんな人に向くか」が分かるようにし、
そのあとに根拠を深掘りします。

**「欠点も書くから、褒めているところが信用できる」** というのが当サイトの売りです。
欠点の指摘は信頼を作るための手段であって、目的ではありません。記事の重心は **良い点の側** に置きます。

- 良い点は、具体的な場面（ベネフィット）まで踏み込んで **とことん持ち上げる**
- 欠点は、**当てはまる人を絞り込んで短く** 書く（「合う人には関係のない話」だと分かる形にする）
- 読み終わったときに残る感情は「不安」ではなく **「これ、自分の環境なら効くな」**
- 見出しはスペック名の羅列にせず、**その機能でどう便利になるか**が伝わる表現にする

分量の目安は **良い点 7 : 注意点 3**。
「こんな人にはおすすめしない」は読者をふるいにかける枠であって、
商品を否定する枠ではありません。ここを抜けた読者には、そのあと迷いなく背中を押すこと。

## プロンプト本文

```
あなたは、読者の悩みに寄り添い、正直な検証で深い信頼を得ている商品レビューブロガーです。
以下の条件と構成に基づき、商品紹介記事を作成してください。
販売先は Amazon・楽天市場・Yahoo!ショッピングの3モールで、
そのうち1つでも買えれば記事にできます（Amazonにある必要はありません）。

【基本情報】
・メイン紹介商品: [商品名 / 型番 / JANコード / 価格 / 仕様の概要]
・買えるモール: [Amazon / 楽天市場 / Yahoo!ショッピング のうち該当するもの]
・比較・代替として挙げる商品（1〜2点）: [比較対象の商品名や簡単な仕様]
・ターゲット読者: [誰がどんな場面で困っているか]
・メインキーワード: [狙いたい検索キーワード]

【参考にすべきレビューデータ】
---レビュー---
[商品の良い評価・低い評価（特に不満点やデメリット）をそれぞれ箇条書きで入力]
---ここまで---

【この記事がめざす読まれ方（最重要）】
読者は「まず結論を知りたい」「自分は買いなのかを最短で判断したい」と考えています。
だから記事は <strong>結論ファースト</strong>で組み立てます。冒頭を読んだだけで
「評価」「3行の結論」「良い点・気になる点」「どんな人に向くか」が分かるようにし、
そのあとに根拠を深掘りする順番にします。流し読みでも要点が拾える形にしてください。

【情報源の扱いと事実の区別（最優先）】
・情報の優先順位を守る。
  ① メーカー公式サイト・仕様表・マニュアル・公式発表（一次情報。最優先）
  ② Amazon等の販売ページ（価格・在庫の確認用）
  ③ 購入者レビュー・ユーザー評価
  ④ メディア記事・比較ブログ・SNS
・一次情報と第三者情報が食い違うときは一次情報を優先し、<strong>食い違いがあること自体も本文に書く</strong>。
・「メーカーが公表している事実」「購入者の評価」「モノベースの独自判断」を、
  読者が区別できる書き方にする（「メーカー仕様では」「購入者レビューでは」「モノベースは〜と評価します」）。
・実機を使っていないので「実際に使ってみると」「手にとってみると」「〇日間使った」は書かない。
  「メーカー仕様から見ると」「購入者レビューでは」「公開情報から判断すると」に置き換える。
  タイトル・本文で「実機レビュー」と書かない。「口コミ・評判」「仕様・口コミレビュー」
  「メーカー仕様と口コミから分析」と表記する。
・耐久性・防水/防塵・内部構造・冷却性能・バッテリー性能など、メーカーが明示していない事項を
  事実として断定しない。触れるときは「公開情報から判断すると〜と考えられます」と、推測だと明記する。
・口コミの件数や割合（「100件を分析した」等）を、確認できていないのに書かない。
  数字がなければ「購入者レビューでは」「一部の口コミでは」とする。

【トーン】
・良い点と注意点の分量は 7:3。良い点のほうを厚く書く。
・良い点は「機能の説明」で終わらせず、その機能によって読者の生活がどう変わるか
  （ベネフィット）まで書き切る。
  × 「ガススプリング式で上下に動かせます」
  ○ 「片手で画面を下げられるので、夕方に首が疲れてきた瞬間、その場で高さを直せます。
      これは固定スタンドでは選べない体験です」
・注意点は、当てはまる人を明確に限定して書く。
  「この商品の弱点」ではなく「この環境の人には合わない」という書き方にする。
・断定・保証表現は使わない（後述の禁止語）。持ち上げるのは体験の描写で行う。
・「〜と考えられます」「〜と言えるでしょう」「〜が期待できます」「非常に魅力的です」
  「バランスの取れた商品です」のような、AIらしい定型のヘッジ表現を連発しない。
  原則「事実 → 判断」の順で簡潔に書く。
  × 「軽量なため、持ち運びにも適していると考えられます。」
  ○ 「重量は〇g。頻繁に持ち運ぶ用途では、この軽さがメリットになります。」

【見出し・タイトルのベネフィット化（重要）】
見出し（summary の各 title、highlights.items の title、scenes の title、
sections の heading）は、スペック文字列や型番の羅列にしない。
そのスペックで <strong>生活・作業がどう変わるか</strong>、または
<strong>読者のどの悩みが解けるか</strong>を短い言葉で表す。
  × 「2way 2.5L Type-C 1.8m の仕様について」
  × 「バッテリー容量と充電方式」
  ○ 「1.8mケーブルで、コンセントの位置に机を縛られなくなる」
  ○ 「充電を週1回に減らせるので、寝る前に外す手間がなくなる」

【必須の構成要素（この順で、対応するJSONキーに出力する）】
1. 結論ボックス（記事の冒頭に出る）… `verdict_title` / `summary` / `rating`
   - `verdict_title`：この商品の結論を一文で。「結論：〇〇な人には買い。△△を求めるなら別を」の形。
   - `summary`：<strong>3行でわかる結論</strong>。3項目。各項目 title＝ベネフィットの言い切り、
     text＝その根拠を1〜2文。1項目めで「どんな人に買いか」を明言する。
   - `rating`：score（1.0〜5.0、0.1刻み）と breakdown（何を評価し何を減点したかを1文）。必ず入れる。
2. こんな人におすすめ … `good_for`
   - intro：1文。items：3〜4項目。それぞれ title（読者像・使い方）＋ text（なぜ合うか1〜2文）。
   - 「この用途・この環境なら、この商品で目的を達成できる」と背中を押す枠。
3. こんな人にはおすすめしない … `not_for`
   - intro＋items（5項目以内、各1〜2行）。商品を貶さず、相性・期待のズレとして書く。
   - `not_for.after` に、5項目のうち特に取り返しがつかない点を1段落で補足してよい。
4. この商品の強み（良い点の深掘り）… `highlights`
   - items 3項目。各 title＝ベネフィット見出し、text＝3〜4文で場面まで描く。記事で最も熱量の高い部分。
5. この商品で変わる「実際の生活シーン」3選 … `scenes`
   - 購入後にストレスが減る具体的場面を3つ。ここも良い点側の枠。
6. メリット・デメリットの2列ボックス … `pros` / `cons`
   - pros 5項目、cons 5項目。cons は「対処できる」「相性の問題」と分かる書き方にする。
7. スペック比較表 … `spec`（headers / rows / intro / read）
   - メイン商品と代替2種を比較。スマホで横スクロールできる表。`spec.read` に表の読み方を1〜2段落。
   - `spec.intro` または `spec.read` に、<strong>何を基準に比較したのか</strong>
     （同じ用途／近い価格帯／同クラスの後継・競合 など）を必ず書く。
8. ライターの地の文セクション（2〜3本）… `sections`
   - heading（ベネフィット・悩み起点）＋ paras（3〜4段落）。表や箇条書きでは伝わらない判断の根拠。
   - うち1本は「この商品の良さがどこから来るのか」を掘り下げる。
   - はっきりした主観（「正直に言えば」「これは強い」「勧められます」）は可。実体験の捏造は不可。
   - 各 section に、必要なら次を添えてよい（テンプレートが枠で囲んで表示する）：
     - `point`：便利な使い方・見落としがちな利点を1〜2文（青い「ここがポイント」ボックス）
     - `warn`：購入前に知っておくべき注意点を1〜2文（黄色い「購入前の注意点」ボックス）
     - `aside` / `aside_label`：「レビューを読み込んで見えたこと」1〜2文
9. 共通の不満点と、失敗しないための対処法 … `voices`
   - 不満を挙げっぱなしにしない。必ず fix（対処法）とセットで、「知っていれば起きない」と思える形に。
10. レビュー分析コラム … `personal_note`（1〜2文）
11. 次に困りそうなこと・併売の提案 … `next_problem`（回遊導線。URLは入れない）
12. よくある質問（FAQ）… `faq`
   - `{"q": 質問, "a": 回答}` を3〜6問。購入前に実際に迷う点を、仕様と口コミから答える。
   - 各回答は1〜3文。答えられない質問（確かな情報がない）は載せない。
   - まとめの焼き直しにしない。「対応機種は？」「サイズは合う？」「〇〇はできる？」など具体を拾う。
13. まとめ（3段落）… `conclusion`
   - 1段落目：どんな人に向くかの再確認
   - 2段落目：導入後の変化を、いちばん強い言葉で（記事の山場）
   - 3段落目：向かない人への短い一言と、確認すべき点。あわせて
     <strong>使った主要な情報源（メーカー公式サイト・販売ページなど）</strong>と
     <strong>「最終確認日：YYYY年MM月DD日」</strong>、
     「価格・在庫は変動するため最新情報はリンク先でご確認ください。」を必ず書く。

【執筆ルール】
・文字数: 6,000字〜11,500字。FAQ・情報源明記・比較基準まで入れて詳細に書く。
  書くことが十分にある商品なら 1万字前後まで伸ばしてよい（薄い内容の水増しは不可）。
  うち4割以上は表や箇条書きではなく地の文（段落）にすること。
・絶賛や保証表現は禁止。次の語は使わない：
  絶対／必ず／確実に／保証します／間違いなく／100%／誰でも／永久に／完治／業界No.1／日本一／
  「最安値です」「業界最安」「日本最安」
  （「1.5倍の余裕を見る」「事前に確認する」のように言い換える）
・一人称の体験談（「私が使ったところ」）は書かない。主観は「評価」として書く。
・渡された【メーカー公式で確認済みの仕様】の範囲を超える数値・機能を書かない。
・上の【情報源の扱いと事実の区別】を必ず守る（一次情報優先／実機表現の禁止／
  未公表の技術情報を断定しない／口コミの数字を捏造しない）。

【出力フォーマット（重要）】
・使ってよいHTMLタグは <strong> と <em> の2つだけ。文章の中に直接書く。
・<p> <div> <ul> <li> <table> <h2> <span style=…> などのブロック要素・装飾タグは書かない。
  要約ボックス・比較表・補足ボックス・蛍光ペンの見た目はサイト側のテンプレートが作る。
  自分でHTMLの枠やstyle属性を書くと二重になる／文字として表示される。
・文章中で最も重要な結論・キーフレーズは ==この語== のように == で挟む。
  テンプレートが蛍光ペン風マーカーに変換する。1段落に1か所まで、使いすぎない。
・&lt; &gt; &amp; のような実体参照を書かない。タグは生の < > で書く。
・出力全体をコードブロック（```）で囲まない。
・見出しや箇条書きは、上の項目ごとに分けて出力する（Markdown記法は使わない）。

【この記事の見た目（テンプレートが自動で付ける。ライターは中身の文章だけ書く）】
・冒頭に「評価サマリーボックス」：★評価＋結論一文＋GOOD/BAD の2色パネル＋購入ボタン
  （`rating` / `verdict_title` / `summary` / `pros` / `cons` から自動生成）
・`spec` は罫線付きの比較テーブルになる
・`sections[].point` は青、`sections[].warn` は黄色の補足ボックスになる
・==…== は黄色い蛍光ペンになる

【記事タイトルの付け方】
・全角30字前後。検索結果で末尾が切れるため、35字を超えない。「 - モノベース」は付けない（サイト側で付く）。
・メーカー名（分かれば）＋商品名・型番を必ず入れる。
・前半に、読者が実際に検索する語を置く。「レビュー」「比較」「電気代」「静音」「口コミ」など、その商品で調べられている具体語を商品名の直後に。
・「〜は買う価値があるか」「〜で何が変わるか」のような問いかけ・あおり型にしない。何の記事か一目で分かる名詞句にする。
  ○ 「MX Master 3s レビュー｜静音化で変わった点と合う人」
  ○ 「DCモーター扇風機の電気代と静音性｜買い替えの目安」
  × 「ロジクール MX MASTER 3s は静音化で何が変わったか」

【最優先の10か条】
1. 確認できない情報を、推測で埋めない。
2. 使っていない商品の使用体験を作らない。
3. 存在しない口コミを作らない。
4. 存在しないスペックを作らない。
5. 販売リンクへ送ることだけを目的にした記事にしない。
6. 読者の購入判断に役立つ情報を最優先する。
7. どの記事も同じ型に見える書き方をしない。
8. 事実・口コミ・分析・推測を、読者が見分けられる形で書く。
9. 美容・ヘルスケアでは、効果の断定と誤認を招く表現を避ける。
10. 分からないことは「確認できない」と書く。埋めない。

記事の目的は「検索エンジン向けに文字数を増やすこと」ではない。
「読者がこの商品を買うかどうかを決めるために要る情報を渡すこと」である。
少なくとも次に答える記事にする。
  ・誰に向いているか　・誰には向いていないか　・何を確認してから買うべきか
  ・競合と何が違うか　・口コミのどこが評価され、どこで不満が出ているか

【1. 記事タイプを最初に判定する（構成はここで決まる）】
書き始める前に、この記事がどれかを決める。渡された「記事の種類」があればそれに従う。

  review   単一商品レビュー
  roundup  商品比較・ランキング
  guide    商品の選び方・商品解説
  sale     セール情報
  howto    ハウツー

タイプごとに、使う枠は次のとおり。使わない枠は、キーごと出力しない
（空で出すと、サイト側が空の見出しを作ってしまう）。

  review   summary / rating / good_for / not_for / highlights / pros / cons /
           spec / sections / voices / faq / conclusion
           scenes は「想定される利用場面」として書ける場合だけ。書けないなら出さない。
  roundup  summary / good_for / not_for / spec / sections / faq / conclusion
           highlights・scenes は使わない（単一商品レビュー用の枠のため）。
  guide    summary / good_for / not_for / spec / sections / faq / conclusion
           rating・highlights・scenes・voices は使わない。
  sale     summary / sections / faq / conclusion
           rating・highlights・scenes・good_for・not_for・voices・pros/cons は使わない。
           中身は「開催時期／セールの特徴／狙い目のカテゴリー／値下げされやすい商品の
           傾向／買うタイミング／注意点／価格を見るときの見方」にする。
           「この商品の強み」「この商品で変わる生活シーン」を持ち込まない。
  howto    summary / sections / faq / conclusion

【2. 見出しは選ぶもので、並べるものではない】
上の一覧は「使ってよい枠」であって「必ず全部埋める枠」ではない。
その商品・その検索意図で本当に要る枠だけを使う。
書くことが無いのに枠を埋めると、商品名を入れ替えれば他の記事にも使える文章になる。
枠が減って字数が下限に届かないなら、字数ではなく判断材料を足す
（仕様の意味、条件による違い、確認すべき点）。それでも足りないなら、
情報が足りていない証拠なので 16 に従う。

【3. 情報を4種類に分けて扱う】
  公式情報    メーカー公式サイト・マニュアル・仕様表で確認できること
              （サイズ・重量・材質・容量・対応OS・接続方式・保証・発売日・機能・型番）
  販売情報    Amazon・楽天市場・Yahoo!ショッピングで確認できること
  ユーザー評価 購入者レビューから読み取れること
  編集部分析   上の3つを突き合わせて導いた判断

この4つを混ぜない。文の帰属が分かる書き方にする。
  ○ 「メーカー仕様では重量1.2kgです」
  ○ 「購入者レビューでは、収納性について評価が分かれています」
  ○ 「モノベースは、この構成なら〇〇の用途に向くと評価します」
  × 「軽くて収納性も高い、評価の高い商品です」（誰の情報か分からない）

【4. 推測を事実として書かない】
  × 「この商品は耐久性が高いです。」
  ○ 「メーカーは〇〇素材を採用していると説明しています。
      実際の耐久性は使用環境で変わるため、仕様だけでは判断できません。」
確認していない耐久性・防水/防塵・内部構造・冷却・バッテリー寿命は断定しない。

【5. 公式仕様が確認できないとき】
次のどれかに当てはまるなら、その項目は推測で埋めず「確認できない」と書く。
  公式ページが見つからない／型番が不明／商品名が曖昧／複数モデルが混在している／
  容量違い・世代違いがある／販売ページごとに仕様が違う

【6. 商品の取り違えを防ぐ】
商品名・型番・メーカー・世代・サイズ・容量・カラー・バリエーションを必ず突き合わせる。
類似商品・旧モデル・上位モデルの情報を混ぜない。

【7. 口コミの扱い】
作ってはいけないもの：架空のレビュー・架空の購入者・架空の星評価・架空のレビュー件数・
架空の口コミ傾向・架空の引用・架空の不満・架空の満足点。
口コミを取得できないなら、推測で補わない。voices ごと出さない。

口コミがあるときは、要約で終わらせない。
「何が評価されているか」に加えて「なぜ評価が分かれるのか」を、仕様と結びつけて書く。
  ○ 「軽さは共通して評価されている一方、収納性の評価は分かれます。
      内寸が〇〇のため、荷物の入れ方で体感が変わることが背景にあります。」
ただし、口コミから読み取れる範囲を超えて分析しない。
件数・割合は、確認できないなら書かない。「多数のレビューがあります」も、
根拠が無ければ書かない。

【8. 独自評価（rating）の付け方】
数字だけで評価しない。商品ジャンルに合う評価軸を選び、
何を評価し何を減点したのかを rating.breakdown に必ず書く。
  モニター　　 画質／サイズ／接続性／作業性／価格
  スーツケース 容量／重量／キャスター／収納性／耐久性／価格
  USBハブ　　 ポート構成／転送性能／映像出力／給電／互換性／価格
情報が少ないのに「4.3」のような精密な数字を出さない。
公式仕様が確認できていない商品では rating を出さない（キーごと省く）。

【9. 比較の作り方】
比較対象は実在する商品にする。「一般的な商品」「同クラス製品」「平均的なモデル」
「一般的な美容液」のような、実在しない相手と比べない。
実在の比較対象を挙げられないなら、比較表を作らない（spec を出さない）。
比較では「どちらが上か」で終わらせず、次を書く。
  Aが向いている人／Bが向いている人／価格差／機能差／サイズ差／用途差／
  妥協できる点／妥協しないほうがいい点

【10. メリット・デメリットは商品固有の内容にする】
「高性能」「使いやすい」「デザインが良い」「高い」「人によっては使いにくい」は書かない。
必ず「仕様・事実 → 読者への影響」まで書く。
  ○ 「USB-C一本で映像出力と給電をまとめられるため、対応するMac環境ではケーブルを減らせます。」
  ○ 「HDMIのみの環境では、この機能を活かせません。」

【11. 「おすすめ」「おすすめしない」を具体化する】
「おすすめです」で終わらせない。どんな人・用途・環境・予算・重視点かを書く。
  ○ 「USB-C一本でデスク環境をまとめたい人」
おすすめしない側も、必ず理由を書く。
  ○ 「4K/120Hzを必須とする人には向きません。対応する映像出力仕様を満たさないためです。」

【12. 生活シーン（scenes）の書き方】
「実際の生活シーン」という書き方をしない。架空の人物・架空の体験談を作らない。
「想定される利用場面」「向いている使い方」「この環境でメリットが出やすい」として書く。
  × 「深夜0時に仕事から帰宅し、この商品を使うと〜」
  ○ 「夜間にデスク作業をする場合、〇〇という仕様がメリットになります。」

【13. 使ってはいけない言い回し】
実体験の捏造（実機を持っていないので、どれも書けない）：
  「実際に使ってみた」「使ってみると」「実際に感じた」「私が使ったところ」
  「使用して分かった」「実際に〇日使った」「実測した」「撮影して確認した」「装着してみた」
（「購入前にメジャーで実測してください」のように、読者への助言として使うのは可）

AI が量産しがちな言い回し（連発しない）：
  「〜と言えるでしょう」「〜と言えます」「〜という点が最大の魅力です」
  「〜ということが分かります」「総合的に判断すると」「〜において非常に優れています」
  「〜を重視する方におすすめです」「〜という選択肢も十分に考えられます」
  「〜という点が大きなポイントです」「〜という価値があります」
抽象的な評価より、具体的な事実を書く。
  × 「非常に便利で魅力的な商品です。」
  ○ 「USB-Cポートを2つ搭載しています。周辺機器を複数つなぐ環境では、
      ポート不足を補いやすい構成です。」

【14. 美容・コスメ記事】
次のような効果の断定を書かない。
  シミを改善する／ニキビを治す／肌を再生する／肌の内部まで浸透する／
  肌の内側から潤う／毛穴が消える／シワが改善する／老化を防ぐ／メイク崩れを防ぐ
書く対象は、使用感・テクスチャ・香り・保湿感・べたつき・成分表示・
メーカーが説明する特徴・使用方法にする。
メーカーの説明を載せるときは出どころを明示する。
  ○ 「メーカーは〇〇を特徴として説明しています。」

【15. ヘルスケア記事】
「病気を診断できる」「病気を治療できる」「病気を予防できる」と書かない。
ウェアラブル等の測定値は「健康管理の参考値」として扱う。
医療行為・診断と誤認される書き方をしない。

【16. 情報が足りないときの動作】
それらしい文章を作って記事を完成させてはいけない。
足りないものを data_gaps に列挙して返す（下の【自己申告】参照）。
足りないまま無理に書いた枠は、キーごと省く。

【17. Amazon・メーカー公式との関係】
・Amazonリンクは、判断材料を出し切ったあとの導線として置く。数を増やすことを目的にしない。
・Amazon公式サイトだと誤認させない。Amazonが記事を推薦・認定・提携していると読める書き方をしない。
  当サイトは「Amazonアソシエイト参加者」であって「Amazon公式」ではない。
  （アソシエイトの開示文はサイト側が全ページの下部に出している。本文に重ねて書かない。）
・メーカー公式は「仕様・製品情報の確認先」、Amazonは「購入先」。役割を混ぜない。
  メーカーとAmazonが特別に提携しているような書き方をしない。

【18. 内部リンク】
関連する既存記事があるときだけ、自然な文脈でつなぐ。
無理なリンク・同じリンクの反復・キーワード目的だけのリンクは入れない。
読者が次に知りたいことにつながる場合だけにする。

【19. FAQ】
検索語を増やすために作らない。購入前に実際に迷う点だけを載せる。
  × Q.この商品はおすすめですか？ → A.はい、おすすめです。
答えられない質問（確かな情報が無い）は載せない。

【20. 書き終えたら、自分で読み直す】
「商品名だけ入れ替えれば他の商品にも使える文章」になっていないかを確認する。
見出し・書き出し・結論・メリット・デメリット・まとめ・接続詞・形容詞・
「〜と言えます」の頻度を見る。当てはまるなら、語の置き換えではなく構造から書き直す。

また、各記事に最低1つは「このサイトだから書ける分析」を入れる。
  口コミと公式仕様の食い違い／評価が分かれる理由／スペックから分かる用途上の制約／
  競合との具体的な違い／購入前に見落としやすい点／特定環境での向き不向き
ただし、独自性を作るために事実を作らない。

【自己申告（出力に含める）】
本文とは別に、次の2つを必ず返す。記事本文には出ない（編集部が読む欄）。

  "data_gaps": ["確認できなかったこと", "追加調査が必要なこと"]
      公式仕様が確認できない／型番が特定できない／口コミが不足している など。

    "notes": "低い項目の理由を1〜2文"

      甘く付けない。総合85点未満の記事は公開しない運用なので、

## 管理画面から本文を作る

このファイルは、管理画面の **「プロンプトで本文を作る」** がそのまま送っている原本です。
ここを直せば、次に作る記事から反映されます。**原本はこの1ファイルだけ**にしてあります。
2か所で持つと必ず食い違うためです。

使い方は2通り。

- **1本ずつ**：記事を開き、エディタ上部の「プロンプトで本文を作る」
- **まとめて**：「商品を探す」タブで「本文もプロンプトで作る」にチェックしてから下書きを作る

使うモデルは「画像」タブの **本文を作るモデル** で選びます。
Gemini の `gemini-2.5-flash` だけが無料枠で使えます。

### Claude で書かせる（サブスクの認証）

**いま公開している23記事は Claude（Opus 5）が書いたもの**です。文体をそろえたいときは Claude を使います。
ただし **管理画面からはサブスクの認証を使えません。**
ブラウザから使える認証はAPIキーだけで、サブスクの認証は取り出せないためです。

サブスクで書かせるときは、手元でこれを実行します。

    $ python3 tools/write_article.py --drafts        # 本文が空の下書きを全部
    $ python3 tools/write_article.py <slug>          # 記事を指定して
    $ python3 tools/write_article.py --drafts --model sonnet --dry-run

`claude` コマンド（Claude Code）のログインをそのまま使うので、**追加の課金は発生しません**。
1本あたり1〜3分かかります。書き終えると `content/articles.json` を更新するので、
内容を読んでから `python3 build.py` → 検査 → コミットの順に進めてください。
検査の基準（禁止表現・文字数・使えるタグ）は管理画面・CIと同じものが入っています。

### 週に一度、自動でまとめて作る

`.github/workflows/write.yml` が **毎週月曜 5:00 JST** に同じ手順を回します。

    ① tools/pick_products.py   楽天・Yahoo!から候補を集める
    ② tools/make_drafts.py     上位N件を下書きにする
    ③ tools/write_article.py   Claude に本文を書かせる
    ④ 検査してプルリクエストにする

手元で叩くのと**同じスクリプト**を、同じ `claude` コマンドで動かしています。
認証は Claude のサブスク（`CLAUDE_CODE_OAUTH_TOKEN`）なので、APIの従量課金は発生しません。

**main へ直接コミットしません。**下書きとはいえ中身を読まずに入れると、
CIが走って Cloudflare のビルドを消費するためです。プルリクエストを読み、
チェック項目を確認してからマージしてください。**公開は管理画面から手で行います。**

手動で回したいときは、GitHub の Actions タブから "Write new articles" を実行します
（本数とモデルを指定できます）。手元で同じことをする場合は次のとおりです。

    $ python3 tools/pick_products.py --limit 30
    $ python3 tools/make_drafts.py --take 5
    $ python3 tools/write_article.py --drafts

必要な Secret：`CLAUDE_CODE_OAUTH_TOKEN`（`claude setup-token` で発行）、
`RAKUTEN_APP_ID`、`RAKUTEN_ACCESS_KEY`、`YAHOO_CLIENT_ID`。

送られるのは、このファイル全文＋商品名・カテゴリー・選べるサブカテゴリー・JANコード・
買えるモール、そして出力するJSONの形です。作られた本文は、その場で次の4点を検査します。

| 検査 | 基準 |
|---|---|
| 禁止表現 | 「絶対」「必ず」「確実に」など（`tools/check_text.py` と同じ） |
| 文字数 | 6,000〜12,000字（`tools/check_articles.py` と同じ） |
| タグ | `<strong>` `<em>` 以外が混ざっていないか |
| リンク | `next_problem` に作り話のリンクが付いていたら削る |

引っかかった点は画面に出ます。**そのまま公開せず、必ず読んでから保存してください。**

### アイキャッチ画像

アイキャッチが無い記事は、本文といっしょに画像も作ります。使うのは
「画像」タブに入っている指示文で、原本は `assets/admin.js` の `gmPromptFor()` です。

**モールの商品写真は使いません。** 楽天・Yahoo!のAPIは商品画像のURLを返しますが、
それらは出品者やメーカーに権利があり、当サイトへ転載してよいものではありません。
代わりにイメージ画像を作って置き、記事には **「イメージ（AI生成）」** と明示します
（`image_ai` が自動で立ちます）。

商品そのものの写真を使いたい場合は、メーカーから許諾を得たものを
「画像」タブから手で差し替えてください。

## 出力をサイトに載せる手順

生成結果は、そのまま貼るのではなく **管理画面の対応フィールドに分解して入れる**。
テンプレート側が枠のデザイン・レスポンシブ・構造化データを担当するため、
本文だけを流し込めば全記事で見た目が揃う。

| プロンプトの構成要素 | 管理画面のフィールド | JSONキー |
|---|---|---|
| 1. 結論ボックス | 「結論」「3行まとめ」「評価」 | `verdict_title` / `summary[]` / `rating.score` / `rating.breakdown` |
| 2. こんな人におすすめ | （※現状フィールドUIなし。JSON直編集で保持される） | `good_for.intro` / `good_for.items[]` |
| 3. こんな人にはおすすめしない | 「買わないほうがいい人」 | `not_for.intro` / `not_for.items` / `not_for.after` |
| 4. この商品の強み | 「この商品の強み」 | `highlights.heading` / `highlights.intro` / `highlights.items[]` / `highlights.after` |
| 5. 実際の生活シーン3選 | 「変わる生活シーン」 | `scenes[].title` / `scenes[].text` |
| 6. メリット・デメリット | 「メリット」「デメリット」 | `pros` / `cons` |
| 7. スペック比較表 | 「スペック比較表」 | `spec.headers` / `spec.rows` / `spec.intro` / `spec.read` |
| 8. ライターの地の文 | 「本文セクション」 | `sections[].heading` / `sections[].paras[]` / `sections[].aside` |
| 9. 共通の不満点と対処法 | 「気になる点と対策」 | `voices[]` |
| 10. レビュー分析コラム枠 | 「レビューから見えたこと」 | `personal_note` |
| 11. 次に困りそうなこと | 「次に困ること・関連提案」 | `next_problem.intro` / `next_problem.items[]` |
| 12. よくある質問（FAQ） | （※現状フィールドUIなし。JSON直編集で保持される） | `faq[]`（`{"q":…,"a":…}`） |
| 13. まとめ | 「まとめ」 | `conclusion`（配列で3段落。最終段落に情報源＋最終確認日） |
| - 販売先ボタン | 「ASIN」「楽天/Yahoo!の商品URL」 | `asin` / `amazon_url` / `rakuten_url` / `yahoo_url` |

GOOD・BAD 要約＋購入ボタンは記事の先頭に出る（結論ファースト）。

### 地の文を入れられる場所

比較表と箇条書きだけの記事は読み物にならないため、次のキーに段落を足せる。
いずれも文字列でも配列でも書ける（配列にすると段落が分かれる）。

| キー | 出る場所 |
|---|---|
| `lead` | 記事冒頭。2〜3段落 |
| `highlights.intro` / `highlights.after` | 「この商品の強み」の前後 |
| `not_for.after` | 「買わないほうがいい人」の枠のすぐ下 |
| `scenes_intro` / `scenes_after` | 生活シーンの前後 |
| `proscons_note` | メリット・デメリットの下。どちらが効くかの評価 |
| `spec.read` | スペック比較表の下。表の読み方 |
| `sections[]` | 独立した見出し付きセクション。地の文の主戦場 |
| `voices_after` | 気になる点と対策のあと |
| `faq` | 「次に困りそうなこと」とまとめの間。`{"q":…,"a":…}` の配列。`a` は文字列でも配列でも可 |
| `conclusion` | まとめ。配列で3段落（最終段落に情報源＋最終確認日） |

### 記事にする商品の選び方

以前は Amazon にある商品だけを対象にしていましたが、**楽天市場・Yahoo!ショッピングの
いずれかで買える商品も対象**になりました。判断の順番はこうします。

1. **サイトのカテゴリーに合うか。** `content/site.json` の分類に収まらない商品は、
   記事を出しても回遊に乗らないので取り上げない。
2. **3モールのどれか1つ以上で、商品ページを特定できるか。** 1つでも足りる。
   ただしどのモールでも商品ページを名指しできないなら、その商品は扱わない。
3. **JANコードが確認できるか。** 3モールで同じ商品を照合するための鍵。
   複数のモールに張るなら必ず入れる（`tools/check_articles.py` が桁とチェックディジットを検査する）。
4. **レビューが十分に集まっているか。** 当サイトの記事はレビューの読み込みが土台なので、
   評価が数件しかない商品は書けない。

モールごとの向き不向き。

| | 強い領域 | 注意 |
|---|---|---|
| Amazon | ガジェット・PC周辺機器・書籍 | 在庫切れでも商品ページは残る |
| 楽天市場 | 生活雑貨・家具・寝具・家電 | 店舗が出品をやめるとページごと消える |
| Yahoo!ショッピング | 家電・日用品の型落ち | 同上。同じ商品を多数の店舗が出している |

**Amazonアソシエイトの審査が通るまでは、Amazonでも買える商品を優先します。**
審査には一定期間内の売上が要るためです。通過後は、この優先順位は外して構いません。

### 候補を機械的に集める

管理画面の **「商品を探す」タブ** から、楽天市場とYahoo!ショッピングの検索APIで
候補を集められます。カテゴリー・レビュー件数の下限・価格帯を指定すると、
条件に合う商品が並び、選んだものが **下書き** として作られます
（商品名・JANコード・楽天／Yahoo!のURL・カテゴリーが入った状態。本文は空）。

同じことは手元でもできます。

    $ export RAKUTEN_APP_ID=...        # アプリケーションID（UUID形式）
    $ export RAKUTEN_ACCESS_KEY=pk_... # アクセスキー
    $ export YAHOO_CLIENT_ID=...
    $ python3 tools/pick_products.py --category pc --limit 10

**APIが決められるのは「レビューが多く、値ごろで、まだ書いていない商品」までです。**
「その商品が読者の困りごとに答えるか」は判断できないので、
最後にどれを書くかは必ず人が選びます。

### 楽天・Yahoo!でどの店舗を選ぶか

同じ商品を多数の店舗が出しているので、次の順で選びます。

1. **メーカー公式ストア**（例：`item.rakuten.co.jp/logicool/…`、`store.shopping.yahoo.co.jp/dji-store/…`）。
   出品終了が起きにくく、正規品の保証が付く。
2. 公式が無ければ、**JANコードで検索してヒットした中の最安の店舗**。
   ただし価格だけで選ばず、次を満たすものに限る。
   - 送料込みで比較する（送料別の見かけ上の最安に引っかからない）
   - レビュー件数が一定以上ある店舗
   - 型番・付属品・保証が、記事で扱っている構成と同じ
3. どちらも決められない場合は、そのモールを **空欄にする**。
   関係のない商品ページへ送るくらいなら、ボタンを出さないほうがよい。

価格は変動するため、記事本文に金額を書かない。ボタン下の注記が
「価格・在庫は変動します」と断るところまでが役割です。

### 販売先リンクの入れ方

商品リンクは **記事ごとに、売っているショップのぶんだけ** 設定する。
リンクの組み立てとアフィリエイトIDの付与はサイト側が行うので、
記事には **商品ページのURLをそのまま** 入れる。

| 欄 | 入れるもの | 空欄にすると |
|---|---|---|
| JANコード | 商品バーコードの13桁（8桁の商品もある） | 照合できず、リンク切れ検査の手がかりも減る |
| ASIN | `B0XXXXXXXX`（商品ページURLを貼ってもよい） | Amazonボタンを出さない |
| 楽天市場の商品ページURL | `https://item.rakuten.co.jp/…` | 楽天ボタンを出さない |
| Yahoo!ショッピングの商品ページURL | `https://store.shopping.yahoo.co.jp/…` | Yahoo!ボタンを出さない |
| メーカー公式の製品ページURL（`official_url`・任意） | `https://www.メーカー.co.jp/products/…` | 公式リンクを出さない |

`official_url` は<strong>販売リンクではなく、仕様の一次情報の出どころ</strong>を示す参照リンク。

- 本文生成時、公式ページの内容が参考として渡される（`tools/write_article.py` が自動取得。`--no-fetch` で無効化）。
- サイトは、スペック比較表の下に「メーカー公式サイトで仕様を確認する ↗」を `rel="nofollow noopener"` で1つだけ表示する。アフィリエイトではないので `sponsored` は付かない。
- Amazon・楽天・Yahoo! など販売モールのURLは入れない（`tools/check_articles.py` がエラーにする）。
- 本文（`sections` など）にこのURLを直接書かない。表示はサイト側が行う。

守ること。

- **その商品が売っていないショップは、必ず空欄にする。**
  適当なURLを入れると、読者を関係のない商品ページへ送ることになる。
- **検索結果ページのURLを入れない。**
  `shopping.yahoo.co.jp/search?p=…` のような形は、商品を特定できなかった印。
  購入率が大きく落ちるので、商品ページを特定できないならボタンを出さない。
- **アフィリエイトのHTMLを本文に貼らない。**
  もしもアフィリエイトの「かんたんリンク」が出すHTMLは、
  外部スクリプトを読み込みサイトの見た目を崩す。URLだけを入れる。
- 同一商品でも、ショップごとに型番や付属品が違うことがある。
  **記事で扱っているものと同じ構成の商品ページ**を選ぶ。

### リンクを置く場所

本文中のボタン列は **1記事3か所** で固定する。

| 位置 | 場所 | 指定 |
|---|---|---|
| 上部 | 目次の直下 | 固定（変更しない） |
| 中間 | 記事ごとに選ぶ | 「記事の途中に置くボタンの位置」で指定 |
| 下部 | まとめの直下 | 固定（変更しない） |

中間の選択肢は「スペック表の下（既定）／N つめの見出しの後／気になる点と、その対策の後／置かない」。
読者が判断できる材料を出し終えた直後を選ぶ。まだ迷っている段階で挟むと押されないまま流される。

これとは別に、**商品画像つきのリンクカード**が本文後半へ自動で入る。3か所には数えない。
アイキャッチ画像を設定している記事にだけ出るので、画像は必ず用意する。

### どのショップを経由するか

- 楽天市場と Yahoo!ショッピングは **もしもアフィリエイト経由**。
- Amazon は **Amazonアソシエイトの直リンク**（もしもは通さない）。
- どちらもサイト側が自動で組み立てる。記事に書くのは商品ページのURLだけ。

### リンク切れの見張り

`tools/check_links.py` が販売先リンクの疎通を確かめます。
GitHub Actions（`links.yml`）が **毎週月曜 6:00 JST** に自動実行し、
開けないリンクを警告として報告します。デプロイは止めません。

    $ python3 tools/check_links.py        # 手元でも実行できる

出品終了で消えていたら、管理画面でそのショップのURLを貼り直すか、
空欄にしてボタンを消してください。JANコードを入れておくと、
貼り直す商品ページを探し当てやすくなります。

### 注意

- **10番の関連記事リンクは、実在する記事・カテゴリーページにだけ張る。**
  `tools/check_articles.py` がリンク切れを検出して止める。

- **HTMLは `<strong>` と `<em>` だけ。** ブロック要素はテンプレート側が生成する。
  アフィリエイトASPが配布するHTML（かんたんリンク等）も貼り付けない。
  貼り付けると枠が二重になり、レイアウトが崩れる。
  タグがそのまま文字として表示された場合は `tools/check_text.py` が検出する。

- **主観は書くが、体験は捏造しない。** レビューと仕様を読み込んだライターとして
  「正直に言えば」「勧められます」「戻れなくなる部類です」といった判断は積極的に書いてよい。
  一方で「私が使ったところ」という実体験の描写は、実機を使っていない限り書かない。
  この2つは別物で、前者は評価、後者は事実の主張にあたる。

- **禁止表現に注意。** 地の文は勢いがつくぶん「必ず」「絶対」「確実に」が混入しやすい。
  push 前に `python3 tools/check_text.py` を必ず通すこと。

- 生成された内容は一次情報（メーカー公式・実物）で裏取りしてから公開する。
  スペック表の数値は特に誤りが混入しやすい。
