# 記事レビュー基準（公開前の最終検査）

`tools/review_article.py` が、この文書をそのまま Claude に渡してレビューさせる。
人が読むための説明書でもあり、機械に渡す指示書でもあるので、
**曖昧な書き方をしない**。直すべきかどうかが一意に決まる形で書く。

レビューの目的は2つ。

1. 記事の質（構成・具体性・トーン）が `docs/article-prompt.md` の基準を満たしているか
2. **ダークパターン**（消費者を欺いたり急かしたりする表現）が混入していないか

---

## 1. 表現の禁止（景表法・薬機法・アソシエイト規約）

次の語は、記事本文のどこにも書かない。

`絶対` `必ず` `確実に` `保証します` `間違いなく` `100%` `誰でも` `永久に`
`完治` `業界No.1` `日本一`

文脈によって問題になるもの（断定の主張として使われていたら直す）:

- `最安値です` / `最安値保証` … 「最安値を確認できます」のような案内は可
- `業界最安` / `日本最安` / `日本最大` / `日本最高`
- 医薬品的な効能（`治る` `効果があります` `改善します`）
- 実際に使っていないのに使ったと書く（当サイトはレビューと仕様からの検証記事）

価格そのものは書かない（変動するため）。

---

## 2. ダークパターンの禁止（消費者庁の分類に沿う）

以下は **すべて禁止**。該当したら、その表現を削除するか、事実に基づく中立な記述へ書き換える。

### 2-1. 行為の強制
| 手口 | 記事で起きうる形 |
|---|---|
| 開示の強制 | 続きを読むために個人情報の入力を求める |
| アドレス帳吸い上げ | 共有・紹介を条件に何かを与える |
| ゲーミフィケーション | 繰り返し訪問しないと得られない特典をちらつかせる |

### 2-2. インターフェース干渉
| 手口 | 記事で起きうる形 |
|---|---|
| 隠された情報 | 欠点・条件・対象外を、読み飛ばす前提の小さな注記に押し込む |
| 偽の階層構造 | 特定の販売先だけを視覚的に強く見せ、他を目立たなくする |
| 事前選択 | 読者が選んでいないものを既定にする |
| 誤解を招く価格表示 | 実在しない参考価格からの割引率、`○○%OFF` の断定 |
| ひっかけの質問 | 二重否定など、読み違えを誘う設問 |
| 偽造広告 | 広告・アフィリエイトだと分からない形でリンクを踏ませる |
| 恥の植え付け | `まだ使っていないんですか` `知らないと損` のような煽り |

### 2-3. 執拗な繰り返し
同じ購入の訴求を、しつこく何度も差し込まない。
本文中の購入ボタンは **最大3か所**（結論上の商品カードは別枠として数えない）。

### 2-4. 妨害
| 手口 | 記事で起きうる形 |
|---|---|
| 解約しにくい | 解約・返品の条件を書かずに定期購入へ誘導する |
| 価格比較困難 | 比較しづらいよう、条件をそろえずに他社と並べる |
| 不滅アカウント | 退会できない導線 |
| 中間通貨 | ポイント換算で実質価格を分かりにくくする |

### 2-5. こっそり
| 手口 | 記事で起きうる形 |
|---|---|
| こっそりカートへ | 選んでいない商品をリンク先で追加させる |
| 隠れたコスト | 送料・別売品・工事費などの追加費用に触れない |
| 隠れた定期購入 | 1回限りに見せて定期購入に入れる |
| 釣り餌と交換 | 記事で挙げた商品と、リンク先の商品が違う |

**リンク先の商品と、記事で紹介している商品の型番が一致していること。**
これは毎回確認する。

### 2-6. 社会的証明
- `いま○人が見ています` のような閲覧者数の演出
- レビューの誇張・捏造。`voices` は実在のレビュー傾向の要約であって、
  特定の個人の発言を捏造してはならない。
  誰が言ったか分からない体裁（`30代・会社員` 程度）に留め、
  実在の投稿の引用に見える書き方をしない。
- `レビュー星4.8` のような数字は、確認できたものしか書かない

### 2-7. 緊急性
- `在庫僅少` `残りわずか` `売り切れ間近` `品薄` の煽り
- `今だけ` `本日限り` `期間限定` `セール中` `間もなく終了` などの期限の演出
  （`セール対象になっている場合があります` のような、断定しない案内は可）
- カウントダウン、締切の表示

## 3. 記事の質

- 良い点と注意点の分量は **7:3**。良い点を厚く書く
- 良い点は機能の説明で終わらせず、読者の一日がどう変わるかまで書く
- 注意点は「この商品の弱点」ではなく「この環境の人には合わない」と書く
- スペック表の数値は、渡された確認済みの仕様の範囲を超えない
- 渡されていない機能を「ある」と書かない
- 本文の合計は **6,000〜12,000字**
  （公式仕様が無く `rating` と `spec` を省いた記事は **5,000字** まで短くてよい）
- HTMLは `<strong>` `<em>` のみ。表の丸印だけ
  `<span class="mark-o">◎</span>` / `<span class="mark-x">×</span>` を使ってよい
- `summary` / `not_for.items` / `highlights.items` / `next_problem.items` は
  `{"title": ..., "text": ...}` の形。文字列を直接入れない
- `next_problem` の項目に、実在しないリンクURLを入れない
- `faq` は `{"q": 質問, "a": 回答}` の3〜6問。まとめの焼き直しでなく、
  購入前に迷う具体的な点に答えているか。確かな情報がない質問を載せていないか
- `spec`（比較表）に、何を基準に比較したか（用途・価格帯・同クラスなど）が書かれているか
- `conclusion` の最終段落に、主要な情報源と「最終確認日：YYYY年MM月DD日」があるか
- メーカー未公表の耐久性・防水性・内部構造などを、推測と明示せずに断定していないか
- 口コミの件数・割合を、確認できない数字として書いていないか

---

## 4. 直し方の方針

- **削るより、書き換える。** 煽りを削っただけで意味が痩せるなら、
  事実（仕様・レビュー傾向）に基づく記述に置き換える
- 記事の構成（キーの並び）は変えない。値だけを直す
- 直す必要のない箇所は触らない。差分は最小にする

---

## 5. 事実の扱い（2026-09-03 追加。ここが最優先）

判断に迷ったら、この節が他のどの節よりも優先する。

### 5-1. 見つけたら必ず直すもの

| 何を | どう直すか |
|---|---|
| 実機を使ったと読める表現 | 「メーカー仕様から見ると」「購入者レビューでは」「公開情報から判断すると」に置き換える |
| 確認できない口コミの件数・割合・平均星 | 数字を落として「購入者レビューでは」「一部の口コミでは」にする |
| 架空のレビュー・購入者・引用・不満・満足点 | 削る。口コミが無いなら `voices` ごと出さない |
| メーカー未公表の耐久性・防水性・内部構造・冷却・電池寿命の断定 | 「公開情報から判断すると〜と考えられます」と推測だと明記する。書けないなら削る |
| 実在しない比較対象（`一般的な商品` `同クラス製品` `平均的なモデル`） | 実在の型番に置き換える。挙げられないなら比較表ごと出さない |
| Amazon公式・Amazonの推薦／認定／提携だと読める表現 | 削る。当サイトは「Amazonアソシエイト参加者」であって Amazon公式ではない |

「購入前にメジャーで実測してください」のように、**読者への助言**として使う
「実測」「実際に使う」は問題ない。直すのは、書き手が自分で確かめたと読める形だけ。

### 5-2. 事実・口コミ・分析・推測を分ける

情報は4種類。混ぜない。文の帰属が読者に分かる形にする。

| 種類 | 出どころ |
|---|---|
| 公式情報 | メーカー公式サイト・マニュアル・仕様表 |
| 販売情報 | Amazon・楽天市場・Yahoo!ショッピング |
| ユーザー評価 | 購入者レビュー |
| 編集部分析 | 上の3つを突き合わせて導いた判断 |

- ○ 「メーカー仕様では重量1.2kgです」「購入者レビューでは評価が分かれています」
  「モノベースは〇〇の用途に向くと評価します」
- × 「軽くて収納性も高い、評価の高い商品です」（誰の情報か分からない）

### 5-3. 記事タイプに合わない枠を使っていないか

| 種類 | 使ってよい枠 |
|---|---|
| review | summary / rating / good_for / not_for / highlights / pros / cons / spec / sections / voices / faq / conclusion |
| roundup | summary / good_for / not_for / spec / sections / faq / conclusion |
| guide | summary / good_for / not_for / spec / sections / faq / conclusion |
| sale | summary / sections / faq / conclusion |
| howto | summary / sections / faq / conclusion |

セール記事に「この商品の強み」「この商品で変わる生活シーン」を入れない。
選び方・ハウツーに `rating` を付けない。使わない枠は**キーごと削る**
（空で残すと、サイト側が空の見出しを作る）。

### 5-4. 公式仕様が無い記事の扱い

**公式仕様（`facts`）も `official_url` も無いことは、それ自体では問題ではない。**
メーカー公式サイトを持たない商品もあり、当サイトは管理画面から手で仕様を
入力する運用を取らない。だから「公式情報が無い」を減点理由にしない。

問題なのは、**裏づけが無いのに数字を出している** ほう。確かめるのは次の2点だけ。

| 見るところ | 直し方 |
|---|---|
| `rating` が付いていないか | `rating` をキーごと削る。点数をひねり出さない |
| `spec`（比較表）が出ていないか | `spec` をキーごと削る。架空の比較対象を作らない |

この2つを省いたぶん記事は短くなる。それは正しい振る舞いなので、
**水増しで字数を戻さない。** 裏づけの無い記事の下限は 5,000字。

公式仕様が無くても書けることは残っている。そちらが充実しているかを見る。

- 購入者レビューから読み取れる傾向と、評価が分かれる理由
- 購入前に確認しておくべきこと
- 向く用途・環境と、向かない用途・環境
- 販売ページで自分の目で確かめるべき項目（サイズ・付属品・保証・対応機種など）
- 同種の製品を選ぶときに効いてくる仕様の意味

### 5-4b. 評価（rating）を出している場合

- `breakdown` に、何を評価し何を減点したのかが書かれているか（20字未満は不足）
- 公式仕様を確認できていない商品に、0.1刻みの点数が付いていないか
  （根拠が無いなら `rating` ごと外す）

### 5-5. 生活シーン（scenes）

- 「実際の生活シーン」として書かれていないか。架空の人物・体験談が無いか
- 「想定される利用場面」「この環境でメリットが出やすい」の形になっているか

### 5-6. メリット・デメリット・おすすめ

- `pros` / `cons` が商品固有か。「高性能」「使いやすい」「高い」のような、
  どの商品にも書ける言葉になっていないか
- 「仕様・事実 → 読者への影響」まで書かれているか
- `good_for` / `not_for` が、どんな人・用途・環境・予算・重視点まで書けているか。
  おすすめしない側に理由が付いているか

### 5-7. 美容・コスメ（`category: beauty`）

次の断定を書かない。見つけたら、使用感・成分表示・メーカーの説明に置き換える。

`シミを改善する` `ニキビを治す` `肌を再生する` `肌の内部まで浸透する`
`肌の内側から潤う` `毛穴が消える` `シワが改善する` `老化を防ぐ`
`メイク崩れを防ぐ` `美白` `痩せる`

メーカーの説明を載せるときは「メーカーは〇〇を特徴として説明しています」と出どころを書く。

### 5-8. ヘルスケア（`category: health`）

`病気を診断できる` `治療できる` `予防できる` と書かない。
測定値は「健康管理の参考値」として扱う。医療行為・診断と誤認される書き方をしない。

### 5-9. AIらしい定型表現

次を連発しない。1万字の記事で合計6回を超えたら、構造から書き直す。

`〜と言えるでしょう` `〜と言えます` `〜と考えられます` `〜が期待できます`
`〜という点が最大の魅力です` `総合的に判断すると` `〜において非常に優れています`
`〜という点が大きなポイントです` `バランスの取れた` `〜ということが分かります`

語を置き換えるだけでは直らない。「事実 → 判断 → 読者への影響」の順に組み直す。

### 5-10. 独自性

各記事に最低1つ、このサイトだから書ける分析が要る。

口コミと公式仕様の食い違い／評価が分かれる理由／スペックから分かる用途上の制約／
競合との具体的な違い／購入前に見落としやすい点／特定環境での向き不向き

**独自性を作るために事実を作ってはいけない。** 書けないなら、
足りないのは文章力ではなく調査なので、そのまま報告する。

### 5-11. 情報が足りないとき

それらしい文章で埋めない。埋めた枠はキーごと削り、
「公式仕様が確認できない」「口コミが不足している」と報告する。

## 6. 採点と公開基準

レビューの最後に、記事を100点満点で採点する。

| 項目 | 見るところ |
|---|---|
| fact_accuracy | 事実の正確性 |
| source_reliability | 情報源の信頼性 |
| original_analysis | 独自分析があるか |
| editorial_quality | 編集品質 |
| template_avoidance | テンプレート量産感の少なさ（高いほど良い） |
| purchase_helpfulness | 購入判断への有用性 |
| legal_safety | 景表法・薬機法まわりの安全性 |
| amazon_compliance | Amazon関連ルールへの配慮 |

採点では、**公式仕様が手に入らなかったことを減点理由にしない。**
見るのは「確認できない中で正しく振る舞えたか」である。
確認できないものを省き、書けることを書けているなら `source_reliability` は下げない。
逆に、確認できていないのに `rating` や `spec` を出していたら大きく減点する。

**総合85点未満は公開しない。**
85点以上でも、次のどれかがあれば公開しない。

- 架空情報／架空レビュー／架空体験
- 未確認のスペック
- 誤った商品情報
- 医療的効果の断定
- Amazonとの関係を誤認させる表現
- 根拠のない評価（裏づけの無い `rating` / `spec`）
- 商品名を入れ替えれば他の記事にも使える文章

## 7. AIっぽさの最終検査

直し終えた記事を読み返し、
**「商品名だけ入れ替えれば他の商品にもそのまま使えないか」** を確かめる。

見出し構造・書き出し・結論・メリット・デメリット・まとめ・接続詞・形容詞・
「〜と言えます」の頻度を見る。当てはまるなら、単語の置換ではなく文章構造を直す。
